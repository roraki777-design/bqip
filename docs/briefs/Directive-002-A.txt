TEMPORAL METADATA WITH UNKNOWN EFFECTIVE START
============================================================

Use a compatible additive extension of the existing
InstrumentMetadataVersion contract.

Do NOT replace receive time with economic effective time.

Do NOT use onboardDate as the effective start of a later filter state.

Do NOT create an unrelated parallel metadata architecture.

Add:

EffectiveTimeBasis

EFFECTIVE_TIME_BASIS_UNSPECIFIED = 0
EFFECTIVE_TIME_BASIS_VENUE_DECLARED = 1
EFFECTIVE_TIME_BASIS_BQIP_CONFIRMED = 2
EFFECTIVE_TIME_BASIS_UNKNOWN = 3

Existing enum tags must not be renumbered.

Validation:

If basis == UNKNOWN:

effective_from_ns MUST be absent
known_from_ns MUST be present

If basis == VENUE_DECLARED or BQIP_CONFIRMED:

effective_from_ns MUST be present

UNSPECIFIED is not acceptable for a persisted validated metadata
version.

Do not synthesize effective_from_ns from:

- HTTP receive time
- onboardDate
- zero
- process start
- file time

2. METADATA RESOLUTION MODES
============================================================

Preserve the distinction:

AS_LIVED
CORRECTED_RESEARCH

Add an explicit resolver result basis:

MetadataResolutionBasis

EFFECTIVE_INTERVAL
KNOWLEDGE_ONLY

Naming may vary minimally if required by existing conventions,
but semantics must not.

------------------------------------------------------------
AS_LIVED
------------------------------------------------------------

A metadata version with:

effective_time_basis = UNKNOWN

may be eligible ONLY using its knowledge interval:

event_receive_time >= known_from_ns

and, if known_to exists:

event_receive_time < known_to_ns

It must return:

resolution_basis = KNOWLEDGE_ONLY

and expose a quality state equivalent to:

METADATA_EFFECTIVE_TIME_UNKNOWN

Meaning:

BQIP knew this metadata state at that time.

It does NOT mean:

the venue's economic change began at known_from_ns.

If two unrelated UNKNOWN observations are simultaneously eligible
because the knowledge intervals overlap incorrectly:

return ambiguity error.

Do not guess.

------------------------------------------------------------
CORRECTED_RESEARCH
------------------------------------------------------------

An UNKNOWN-effective version is NOT sufficient to establish
historical economic applicability before/independent of its known
time.

CORRECTED_RESEARCH must prefer metadata versions with a known
effective interval.

If no known-effective version covers the requested event time and
only UNKNOWN-effective evidence exists:

return:

METADATA_EFFECTIVE_TIME_UNKNOWN

Do not project the observation backward.

Do not silently fall back to AS_LIVED behavior.

7. B2-02 — DECISION
DEPTH LOGICAL IDENTITY
============================================================

Depth logical identity is SESSION-SCOPED.

Use BQIP-ID-V1 with the ordered semantic components:

BINANCE
USD_M_FUTURES
BTCUSDT
DEPTH_UPDATE
<original_session_id>
<U>
<u>

The exact component labels must follow the Foundation BQIP-ID-V1
canonical preimage rules.

session_id is the ORIGINAL CAPTURE SESSION / CONTINUITY EPOCH.

It is NOT regenerated during replay.

Replay must preserve the original session_id from lineage.

A new reconnect / continuity epoch receives a new session_id according
to the existing Foundation session semantics.

============================================================
8. CROSS-SESSION SEMANTICS
============================================================

Same:

U
u

observed in DIFFERENT original sessions:

=> different logical_event_id

BQIP makes NO cross-session deduplication guarantee for native Binance
depth events.

Do not claim that Binance guarantees U/u global uniqueness beyond what
the official documentation states.

Cross-session economic reconciliation, if ever required, belongs to a
future derived layer and is NOT part of Brief #002.

============================================================
9. FIELDS NOT IN DEPTH LOGICAL ID
============================================================

Do NOT include:

pu
event timestamp
transaction timestamp
price levels
quantities
raw payload hash

inside the logical identity recipe.

They are content/provenance/continuity data, not identity components.

Reason:

If within the SAME original session BQIP observes:

same U
same u

but incompatible:

pu
or payload semantics

it must not manufacture a second valid logical event.

It must surface an identity/content conflict.

Define an additive error/quality condition equivalent to:

VENUE_IDENTITY_CONFLICT

Use existing error-contract conventions and preserve old enum tags.

This conflict is separate from:

VENUE_GAP

Example:

same session_id/U/u
same semantic payload
=> duplicate/re-observation policy

same session_id/U/u
different semantic payload
=> VENUE_IDENTITY_CONFLICT

Do not silently choose one.
